# 风神录 3.5.1：音乐缓冲同步修复

当浏览器回调迟到、音频补充成批进行，或音频设备的进度与游戏计时存在偏移时，旧版可能出现断续杂音。原始 FLAC 解码数据没有因此损坏；问题发生在解码之后的循环播放缓冲。

## 原因与修复

旧版用经过的毫秒数计算音乐播放位置，并据此触发原版的四分之一秒补充通知。实际的 miniaudio 混音器却按读取的样本数推进。时间领先时会覆盖尚未读取的片段；一次较长的时间推进跨过多个通知时，布尔事件还会合并通知，导致漏补片段。

现在带有补充通知的音乐缓冲使用混音器实际的源读取位置。每次混音最多处理 1024 帧，随后检查通知并立即运行原有的 C++ 补充任务，再读取下一块。SDL 队列和确定性音频探针都经过同一入口。音效原有的控制时钟、音乐音量、循环点、淡入淡出及曲目资源保持原有规则。暂停/恢复设备只在状态改变时调用。

这不增加音频缓冲水位，也没有通过降低音量或替换音乐文件掩盖杂音。

## 验证

- 浏览器内将实际混音输出与同一混音器播放完整、不可变 PCM 的结果逐样本比较，包含原采样转换的延迟。
- 正常计时、计时领先 400ms、计时落后 400ms、约 464ms 才推进一次计时、反复暂停恢复：每项输出 882,688 帧（约 20 秒），覆盖多次四秒缓冲回绕和一次曲目循环；修复后全部零差异。
- 修复前，计时领先和长间隔两项出现大量错误样本；正常计时零差异。前后报告记录各自 Wasm 校验值。
- 实际浏览器显示回调为 60、30、15Hz 时，测量窗口中音频回调持续输出，无空白音频块；逻辑保持约 60Hz。测试显式停止与重新开始之间的静音不计入测量窗口。
- 全部 18 首 FLAC 共 60 处解码/定位样本与本地原版 PCM 一致，包括未对齐读取、曲目末尾和反向定位。
- 网页资源更新成功，复用原有 DATA 与音乐，录像原字节保留；离线重开、日文/中文存储分离及音频对象释放验证通过。

复现入口：`portable/check-th10-music-continuity.mjs`、`portable/check-low-cadence.mjs`、`portable/th10-architecture-storage.mjs`、`portable/check-gles-package-update.mjs`。

这是桌面 Chromium 的浏览器验证，未对用户手机进行实机录音。极端主线程阻塞或手机音频驱动导致的设备输出中断，需要另外测量；此次验证证明的是上述缓冲同步错误已修复。
